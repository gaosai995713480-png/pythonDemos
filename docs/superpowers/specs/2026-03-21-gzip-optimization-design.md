# GZip 压缩性能优化设计文档

## 目标
减小后端直出静态资源（JS/CSS）及 RESTful API 数据传输体积，从网络层提升用户首次加载及核心页面（如心动画廊）的响应速度，节省服务器出网带宽损耗。

## 背景
当前架构使用 `FastAPI` 直接作为 Web 服务提供端。所有由 `docs/`（前端静态文件产物存放目录）输出的资源均未开启压缩，这导致在手机端等网络不稳定环境下加载大体积 JS、CSS 时体验不佳。此外，当 API 吐出大量相册 JSON 数组内容时也会冗杂拖慢网络。

## 方案与范围
采用 FastAPI 原生的中间件 `GZipMiddleware`，拦截大块明文网络发包流并做实时动态压缩。该优化无须配置外部 Nginx，保持整体工程在各个环境中运行的一体性。

具体涉及修改的范围仅限于：
- **`backend/main.py`**：引入中间件；添加到 FastAPI 实例管道中；配置忽略碎片数据的阈值。

## 详细设计

### 1. 中间件位置
在跨域中间件 `CORSMiddleware` 附近添加 `GZipMiddleware`。FastAPI 中间件的执行顺序决定了必须将其加入到管线上层才能有效压缩其他应用层的内容。

### 2. 压缩阈值 (minimum_size)
引入时设置 `minimum_size=1000` 字节（1KB）。
- 大于 1000 字节的文件和 JSON 数据将被启动 GZ 压缩。
- 极小体积文件维持原样，避免压缩后体积膨胀和 CPU 的额外开销。

### 3. 未被破坏的部分
此优化单纯作用于通过网络发出时的拦截压缩，后端其他路由处理逻辑、参数类型推断、数据库事务请求完全透明，不受任何业务层面影响。

## 测试与验证标准
1. 在部署或运行本地服务器后，检查发向 `/assets/...css` 以及 `/photos.json` 的接口。
2. 开发者工具 Network Tab 中：
    - `Response Headers` 中是否包含 `Content-Encoding: gzip` 响应头。
    - 资源的传输体积（Size）应当明显小于实际解压后体积。
